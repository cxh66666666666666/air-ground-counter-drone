# 接口分层规范

> 本文件是 W1 产出的**工程规范**，约束本仓跨域接口的形态选择（topic / service / action）。
> **不复述**契约约束；命名空间、坐标系、参数入口等以契约真源 [ROS2迁移交接文档](../ROS2迁移交接文档.md#namespace) 为准。
> 依据 [ADR-0008](../adr/0008-nav2-paradigm-absorption-as-code-principle.md) 吸收矩阵（W1 行）：接口职责划分**对齐 Nav2**。

## 1. 三种接口形态的职责

| 形态 | 语义 | 适用 | 不适用 |
|---|---|---|---|
| **topic** | 持续的、可丢的**数据流** | 周期性状态、传感观测、位姿、跟踪结果 | 需要应答确认、需要最终结果与反馈 |
| **service** | 短时、**一次性请求—应答** | 触发一个立即完成的小操作（如查询健康、请求解锁） | 长耗时任务、需要中途反馈或取消 |
| **action** | 长耗时、可**反馈 + 可取消** | 需要过程反馈与可抢占的任务（如"到达某点"） | 一次性瞬时操作、纯数据流 |

## 2. 选用判据

按顺序自问，命中即停：

1. 是**持续/周期数据流**吗？→ 用 **topic**。
2. 是**短时一次性**、调用方需**等待结果**吗？→ 用 **service**。
3. 需要**过程反馈**或**可取消**、且耗时较长吗？→ 用 **action**。
4. 否则：重新审视是否把两个语义混在了一个接口里。

补充原则：

- **默认 topic**：协同层绝大多数是状态 / 观测数据流，默认 topic；service / action 需有明确理由。
- **一个接口一个语义**：不要把"查询状态"和"下达命令"塞进同一个 service。
- **接口集中**：本仓全部自定义接口集中在 `agc_msgs`（[包边界](./包边界.md)）。

## 3. 本仓示范：协同层 9 个消息

W1 落地的 9 个协同接口均为**周期 topic**，符合判据 1：

- 任务状态：`AgcTaskState`
- 观测数据流：`TargetObservation` / `ObstacleObservation` / `SensorObservation` / `AirObservationArray`
- 跟踪结果流：`TargetTrack` / `ObstacleTrack` / `TargetTrackArray` / `ObstacleTrackArray`

其字段事实由 golden 快照冻结（见 [W1 spec](../../.trae/specs/w1-msgs/spec.md)），本文件不内联字段。

## 4. 边界

- 本文件只定**形态选用原则**，**不定义**任何具体服务 / 动作接口。
- 未来域（空中 / 地面 / RL）引入的 service / action 随其 workstream 落地，并归入 `agc_msgs`。
